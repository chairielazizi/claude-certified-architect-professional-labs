# Claude Certified Architect – Professional (CCAR-P) · Hands-on Labs

One runnable lab for **every objective** in the *Claude Certified Architect – Professional Exam Guide*
(v1.0, effective July 2026, exam code **CCAR-P**). Each lab is a folder named `D<domain>.<n> - <title>`
containing a concept README plus equivalent **Python** and **TypeScript** implementations.

> Exam at a glance: 63 items · 120 minutes · multiple-choice & multiple-response · pass = scaled 720 / 1000.

## Setup

Requirements: **Python 3.10+** and **Node.js 24+** (Node 24 runs `.ts` files natively via type stripping, so no build step).

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Windows (use .venv/bin/python on macOS/Linux)
npm install
```

## Running the labs

Every lab runs **offline by default**: no API key, no cost, deterministic output.

```bash
.venv/Scripts/python "D3.5 - RAG Pipeline - Chunking and Indexing/python/main.py"
node "D3.5 - RAG Pipeline - Chunking and Indexing/typescript/main.ts"
```

Run everything (or a domain / single lab) and get a pass/fail report:

```bash
.venv/Scripts/python run_all.py          # all labs, both languages
.venv/Scripts/python run_all.py D4       # one domain
.venv/Scripts/python run_all.py D2.5 -v  # one lab, show output
npm run typecheck                        # strict type-check of all TypeScript
```

### Going live

Set `ANTHROPIC_API_KEY` (or `LABS_MODE=live`) and the same code calls the real Claude API:

```bash
export ANTHROPIC_API_KEY=sk-ant-...      # PowerShell: $env:ANTHROPIC_API_KEY = "sk-ant-..."
```

`LABS_MODE=offline` forces the mock even when a key is present.

## How offline mode works

`shared/python/claude_client.py` and `shared/typescript/claudeClient.ts` hand every lab a **real**
Anthropic SDK client. Offline, the SDK's HTTP layer is swapped for an in-process mock
(`httpx2.MockTransport` in Python, a custom `fetch` in TypeScript) that answers in the Messages API wire
format. Each lab supplies a small *responder* function with canned, realistic replies. The SDK code you read
is exactly the code that runs live.

The mock also simulates the behaviours architects reason about:

| Simulated | Why it matters |
|---|---|
| Token usage (~4 chars/token) and cost per model | Cost modelling, model selection |
| Prompt caching (cache write, then cache read on identical prefix) | Sample question 2 / D2.5 / D4.5 |
| Per-model latency (Haiku < Sonnet < Opus < Fable) | Accuracy-latency trade-offs (D3.3) |
| `max_tokens` truncation → `stop_reason: "max_tokens"` | Diagnosis (D4.4) |
| SSE streaming for text and tool calls | Perceived latency, tool streaming |
| `count_tokens` endpoint | Context budgeting (D2.4) |

Offline numbers are **illustrative**. Use live mode to get real measurements. Known simplifications of the mock:

- **Caching** honours only the *last* `cache_control` breakpoint (no multi-breakpoint reads, no 20-block
  lookback) and uses a 1,024-token minimum. The real minimum is model-dependent and lower on current models.
- **Latency** is simulated per model and scaled down for speed. `elapsed_ms()` scales it back up, so
  interpreter and timer noise is magnified too. Labs that make latency-based decisions model latency
  deterministically from `usage` instead.
- **Errors**: the mock only returns 200/404. Labs that teach 429/529/timeout handling raise the SDK's own
  exception classes from a fault-injection layer (see D5.2, D4.6, D7.3).
- **Not served offline**: Batches, Files, Models API, Skills, MCP connector and server tools (web search, code
  execution, tool search). Labs guard these with `is_live()` and print the exact request code instead.
