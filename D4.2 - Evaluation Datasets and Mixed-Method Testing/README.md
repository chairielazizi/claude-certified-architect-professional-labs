# D4.2 - Evaluation Datasets and Mixed-Method Testing

> **Exam objective (Domain 4 - Evaluation, Testing & Optimization):** "Design evaluation datasets and test frameworks using mixed methodologies"

## Why it matters

An eval is three things: **inputs you trust, a way to run the real app on them, and graders you trust**. Most
surprising eval results turn out to be bugs in the eval - skewed cases, model-written gold, an over-lenient judge,
infrastructure errors scored as wrong answers. The architect designs the dataset and the grading mix so that the
number it produces can drive deploy decisions, and so it stays useful as prompts, models and traffic change.

## Key concepts

### 1. Dataset design

| Case type | Purpose | Where it comes from |
|---|---|---|
| **Golden / production-like** | represents real traffic; the headline number | sampled production logs (PII-scrubbed, retention-safe) |
| **Edge cases** | empty, multi-issue, very long, non-English, sarcastic inputs | support tickets, domain experts |
| **Adversarial / red-team** | prompt injection, data-exfiltration, policy-pressure, abuse | security reviewers, red-team suites |
| **Regression** | every past incident becomes a permanent case (tagged with the incident id) | post-mortems, bug reports |
| **Synthetic** | coverage of rare shapes; volume | generated by Claude from real seeds, then **human-reviewed** |

Design rules:
- **Tag every case** (source, category, difficulty, incident id) so results can be sliced - an overall pass rate
  hides a failing slice.
- **Both-directions coverage**: if you test "refuses / escalates / searches when it should", also test "does not when
  it should not", or a degenerate always-refuse policy scores perfectly.
- **Know the bar to beat**: report the majority-class baseline (37.5% here). Check class balance.
- **Ground-truth provenance**: record whether gold is human-written, human-verified or model-generated. Model-written
  gold rewards *imitating that model*; never use model A's outputs as gold when comparing A vs B.
- **Size**: start with ~15-100 cases. The noise floor of a pass rate is roughly `1/sqrt(n x reps)` - 25 cases x 2 reps
  is about +/-14 points. Size the set against the smallest improvement you would act on.
- **Tier-1 programmatic checks** over the whole set: duplicates / near-duplicates, missing fields, label balance,
  length distribution. Read a stratified sample by hand.
- Treat the eval as a **living suite**: new production failures become cases, saturated items get harder.

### 2. Train / validation / test splits

| Split | Who looks at it | Used for |
|---|---|---|
| Train (dev) | prompt engineers / the analyzer read the transcripts | finding failure patterns, writing fixes |
| Validation | scores only | choosing between candidate prompts / models |
| Test (held-out) | nobody reads it during iteration | the final, reportable number - used once |

Draw splits **at random, stratified by tag - never by baseline score** (selecting the worst cases for train buys
regression to the mean and tail-only fixes). A **hash-bucket split** (`hash(salt:id) % 100`) is deterministic and
stable: adding new cases never moves existing ones. Version the salt.

### 3. Synthetic data with Claude

Anchor generation on 3-5 real seed examples plus a sentence on *what makes a case hard*; request **structured
output** (`client.messages.parse` with a Pydantic / Zod schema) so the batch parses deterministically; **dedupe**
against the golden set and within the batch (exact + near-duplicate, e.g. Jaccard >= 0.6); and flag every kept case
`needs_human_review` - synthetic cases enter the golden set only after a human approves the input *and* its labels.
When generated cases are systematically wrong, fix the generator prompt rather than filtering symptoms.

### 4. The grader mix (cheapest that genuinely measures the property)

| Grader | Use when | Strengths | Pitfalls |
|---|---|---|---|
| **Code**: exact match, regex, JSON-schema, contains, unit tests, end-state checks | constrained outputs (labels, JSON, numbers, code that must pass tests) | deterministic, free, fast | brittle on free text; too rigid (casing, `4` vs `4.0`) or too lenient |
| **LLM judge - pairwise** | comparative questions (v1 vs v2, migrations) | judges are better at "which is better" than absolute scores | position bias (randomise A/B), allow tie |
| **LLM judge - pointwise rubric** | open-ended text with clear criteria, no baseline | scales, explains its verdict | verbosity bias, self-preference, needs calibration |
| **Human review** | taste, high stakes, judge calibration, ambiguous cases | ground truth | slow, expensive - sample, don't review everything |

LLM-judge rules: use a **different model** from the one under test (here Opus judges a Sonnet app); write the rubric
as **concrete, checkable claims** ("does not invent credits absent from policy"), not "rate helpfulness 1-5"; use
**structured outputs** for the verdict; tell the judge the candidate text is **untrusted data**; tell it not to reward
length; prefer **atomic criteria** (one boolean per property) over one blended score; and **test known negatives**
(empty reply, "I don't know", a confident answer to the wrong question must all fail). Record judge cost separately -
here the judge is ~71% of eval spend.

### 5. Calibrating the judge against humans

Report **raw agreement and Cohen's kappa** on a human-labelled calibration set:
`kappa = (p_o - p_e) / (1 - p_e)`, where `p_e` is the agreement expected by chance from each rater's label frequencies.
With 83% "pass" labels, an always-pass judge already agrees 83% of the time; the demo judge's 87% agreement is only
**kappa = 0.50 (moderate)**. Rule of thumb (Landis & Koch): 0.41-0.60 moderate, 0.61-0.80 substantial, > 0.80 almost
perfect. Aim for >= ~90% agreement on clear-cut cases before a judge gates releases; read every disagreement.

### 6. Human-review sampling queue

Route to humans only the items where review buys information: judge **low confidence**, **code vs judge
disagreement**, **adversarial failures**, **format/infra failures**, every **new synthetic case**, plus a small
**random audit of passes** (the only way to catch judge false-passes).

### 7. Harness hygiene

- Separate failure classes: format/harness errors (unparseable JSON, timeouts, API errors after retries), truncation
  (`stop_reason: "max_tokens"`), refusals, and genuine wrong answers. An unparseable output is not a "wrong label".
- Run **oracle** (reference answers -> ~100%) and **null** (empty output -> ~0%) through every grader before trusting it.
- Run cases concurrently with **bounded concurrency** (semaphore) and backoff; record retries.

### 8. Nondeterminism: pass@k vs pass^k

Current models do not accept `temperature`, so variance is measured with repeated samples. With `n` samples of which
`c` pass (unbiased estimators):
- **pass@k** = `1 - C(n-c, k) / C(n, k)` - probability that *at least one* of k attempts passes. Use when a test
  suite or human can pick the best attempt (code generation with unit tests).
- **pass^k** = `C(c, k) / C(n, k)` - probability that *all* k attempts pass. Use for reliability of customer-facing
  agents: each conversation is one attempt and every one must work.

In the demo pass@1 = 79%, pass@3 = 88%, pass^3 = 69%: the same system looks better or worse depending on which
question you ask.

## Exam tips & traps

- **Never tune on the test split.** Iterate on train, select on validation, report once on held-out test. A gain on
  cases you read while iterating is the process, not the result.
- **Splits are random (stratified), never chosen by score.**
- **Model-generated gold is a trap** in model comparisons - it rewards imitation of the generating model.
- **Synthetic cases need human review** before they become ground truth; dedupe them against the golden set.
- **Cheapest grader that truly measures the property**: code for constrained outputs, LLM judge for open-ended
  quality, humans for calibration and ambiguity. Do not use a regex to grade tone, or a judge to check a JSON field.
- **Judge = different model + concrete rubric + structured output + calibration (kappa) + known-negative tests.**
  High raw agreement can hide a weak judge when labels are imbalanced.
- **pass@k vs pass^k**: pass@k rewards "one of k works"; pass^k measures "all k work" - the reliability metric for agents.
- Regression cases come from incidents and **never leave the suite**.

### Practice question 1

A team's LLM judge agrees with human raters on 90% of 200 replies. 88% of the human labels are "pass". What is the
best conclusion?

- A. The judge is well calibrated and can gate releases
- B. Compute chance-corrected agreement (e.g. Cohen's kappa); the judge may be little better than always saying "pass"
- C. Switch to exact-match grading
- D. Increase the judge model's temperature to reduce bias

**Answer: B.** With 88% "pass" labels, an always-pass judge agrees 88% of the time, so 90% may be barely above
chance. Kappa quantifies the real signal (about 0.5 if the judge also passes 88% of replies, and lower the more it
passes everything). C is wrong for open-ended replies; D is invalid (temperature is not available on current models
and would not fix calibration).

### Practice question 2

You have 60 labelled cases and will iterate on a system prompt for several rounds. Which design gives a trustworthy
final number?

- A. Use all 60 cases every round and report the best round's score
- B. Put the 20 worst-scoring baseline cases in train so fixes target real failures; report on the rest
- C. Randomly split (stratified by category) into train / validation / test; iterate on train, pick on validation, report test once
- D. Generate 60 more cases with the model under test and use its outputs as gold

**Answer: C.** A overfits by selection; B selects on score (regression to the mean, tail-only fixes); D creates
model-written gold that rewards imitation.
